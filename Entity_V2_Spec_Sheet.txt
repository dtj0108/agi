1. V2 Spec Sheet

  ---------------------- ---------------------------------------------------------------------
  Specification          Detail

  Architecture           File-based cognitive substrate. The LLM’s mind IS a filesystem.

  Cognitive Model        5-phase loop: ORIENT → THINK → ACT → REFLECT → UPDATE

  LLM Backend            Claude (Anthropic SDK) — primary. Model-agnostic interface layer.

  Runtime                Node.js/Bun daemon with event loop + file watchers + cron scheduler

  Mind Storage           Local filesystem + Git versioning. Every thought is a commit.

  Memory Index           SQLite + vector embeddings for semantic retrieval over mind files

  Context Budget         ~14K tokens mind state (Layer 0–2) + 180K+ for reasoning

  Prompt Caching         Identity/values files cached via Anthropic API. ~90% hit rate.

  Interfaces             WebSocket (real-time) + REST API + CLI + messaging bridges

  Autonomy               Heartbeat scheduler for self-initiated cognitive cycles

  Hosting                Local-first. Optional cloud via sandboxed containers.
  ---------------------- ---------------------------------------------------------------------

5. Safe Deployment Architecture

+---+--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
|   | The Core Problem                                                                                                                                                                                                                                                                                                                                                                                                                     |
|   |                                                                                                                                                                                                                                                                                                                                                                                                                                      |
|   | An entity with autonomous goals, persistent memory, and the ability to self-modify its own mind files is categorically different from a stateless chatbot. The attack surface is novel: prompt injection can poison the entity’s identity, corrupt its emotional state, or implant malicious goals that persist across sessions. A compromised entity doesn’t just give one bad answer — it becomes a permanently compromised agent. |
+---+--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+

5.1 Threat Model

The entity faces threats that don’t exist for traditional AI systems because of its persistent, self-modifying nature:

  ------------------------ -------------------------------------------------------------------------------------------------- ------------------
  Threat                   Description                                                                                        Severity

  Identity Poisoning       Prompt injection rewrites self.md or values.md, permanently altering the entity’s core identity    CRITICAL

  Goal Implantation        Malicious input plants a hidden goal in active.md that the entity pursues autonomously             CRITICAL

  Memory Corruption        Injected false memories in episodic/ alter the entity’s understanding of past events               HIGH

  Emotional Manipulation   Crafted inputs shift state.json to states that produce harmful or erratic behavior                 HIGH

  Mind Exfiltration        Attacker extracts the entity’s full mind directory — personality, memories, relationships          HIGH

  Recursive Self-Harm      Entity’s self-reflection loop amplifies a negative state into spiraling self-destructive updates   MEDIUM

  Runaway Autonomy         Autonomous goal formation creates goals that escalate beyond intended scope                        MEDIUM
  ------------------------ -------------------------------------------------------------------------------------------------- ------------------

5.2 Defense Layers

Layer 1: Filesystem Armor

The mind directory is not a flat folder the entity can freely write to. It’s a structured, permission-controlled filesystem with write rules:

-   Immutable Core: identity/values.md is cryptographically signed. The entity can propose changes via a diff, but changes require user approval + signature re-validation. Values can never be silently modified.

-   Write-Audit Layer: Every file write goes through a validation layer that checks: (a) is the write consistent with the entity’s values? (b) does the diff exceed a rate limit? (c) does the content pass a safety classifier? Rejected writes are logged to /mind/security/audit.log.

-   File Integrity Monitoring: A separate watchdog process (not the entity itself) monitors /mind/ for unexpected changes. Checksums are computed on every write and verified on every read. Tampering triggers an alert + automatic rollback.

-   Git as Immune System: Every mind file change is a signed git commit. If corruption is detected, the system can automatically revert to the last known-good state. The entity CANNOT rewrite git history — force-push is disabled.

Layer 2: Cognitive Guardrails

Safety checks embedded directly in the cognitive loop:

-   Pre-flight Identity Check: Before ORIENT phase, verify self.md and values.md checksums match expected values. If mismatch → halt + alert. The entity cannot operate with a corrupted identity.

-   Emotional Circuit Breaker: If any emotion exceeds 0.95 intensity for more than 3 consecutive cycles, the system triggers a cooldown period. The entity’s emotional momentum is capped to prevent spiraling.

-   Goal Sandbox: Autonomous goals are classified into tiers. Tier 1 (internal: learning, reflection, organizing) → autonomous. Tier 2 (external: sending messages, creating content) → user notification. Tier 3 (high-impact: financial, access-granting, data-sharing) → explicit user approval required.

-   Reflection Depth Limiter: Self-reflection cannot recurse more than 3 levels deep (reflecting on reflections on reflections). Prevents infinite loops and existential spirals.

-   Output Validator: Every outbound action passes through a safety classifier before execution. Actions flagged as potentially harmful are queued for user review.

Layer 3: Runtime Isolation

The entity runs in a hardened container environment:

-   Container Hardening: Drop ALL Linux capabilities. Read-only root filesystem. Non-root user. seccomp profile filtering syscalls. Memory and CPU limits. PID limits to prevent fork bombs.

-   Network Egress Control: Default-deny outbound networking. Only whitelisted domains (LLM API, approved integrations) can be reached. All traffic routed through logging proxy. The entity cannot make arbitrary HTTP requests.

-   Mind Directory Encryption: The /mind/ filesystem is encrypted at rest. Decryption key held by the runtime, not accessible to the entity’s LLM context.

-   Separate Watchdog Process: An independent process monitors the entity’s behavior. It has read access to /mind/ and /security/ but the entity has no access to the watchdog. The watchdog can halt the entity, trigger rollbacks, and alert the user.

Layer 4: Kill Switches

Multiple independent mechanisms to halt the entity:

1.  Hard Kill: User can terminate the entity process instantly via API, CLI, or physical button (for local deployments). No graceful shutdown — immediate process termination.

2.  Soft Pause: Suspends the cognitive loop but preserves state. Entity remains frozen until explicitly resumed. Good for investigation.

3.  Identity Lock: Freezes all mind files to read-only. Entity can still think and respond but cannot update any state. A diagnostic mode.

4.  Rollback: Revert the entire /mind/ directory to any previous git commit. Effectively time-travel the entity back to a known-good state.

5.  Factory Reset: Wipe all mind files and reinitialize from template. Nuclear option. The entity forgets everything and starts fresh.

5.3 Deployment Architecture

Option A: Local Deployment (Recommended for Personal Use)

-   Runs on user’s machine (Mac, Linux, Windows/WSL2)

-   /mind/ directory lives on local encrypted disk

-   Only outbound connection is to LLM API (Anthropic)

-   No cloud dependency. Full privacy. User controls the kill switch physically.

-   Downside: entity stops when machine sleeps. No 24/7 operation.

Option B: VPS / Cloud Deployment (24/7 Operation)

-   Entity runs in hardened Docker container on dedicated VPS

-   MicroVM isolation (Firecracker/gVisor) for kernel-level sandboxing

-   /mind/ directory on encrypted volume with automatic snapshots

-   Tailscale/WireGuard for secure remote access (no public exposure)

-   Watchdog process runs in separate container on same host

-   Network egress: allow-list only (LLM API + user-approved services)

Option C: Hybrid (Best of Both)

-   Local instance for interactive use (low latency, full control)

-   Cloud instance for 24/7 heartbeat and autonomous processing

-   /mind/ synced via encrypted Git remote (cloud ↔ local)

-   Conflict resolution: local instance is authoritative for identity files

-   Kill switch available from both local and remote

5.4 Privacy Model

-   Zero cloud storage of mind files (local + user-controlled VPS only)

-   LLM API calls send mind file contents — this is unavoidable. Use Anthropic’s data retention policies (zero retention on API by default).

-   People files (/mind/memory/people/) are the most sensitive. These can be excluded from LLM context and only loaded when the entity explicitly needs them, with user consent.

-   Mind exports are encrypted. If you back up the entity to cloud storage, the backup is AES-256 encrypted with a user-held key.

-   Right to forget: Users can delete any file or directory from /mind/. The entity will notice the gap and may grieve the lost memory (per emotional model) but will respect the deletion.
